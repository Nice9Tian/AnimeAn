# 长时间工作（long_time_work）

Agent 连续工作几小时到几天、用户不在旁边时的规矩。目的只有一个：工作不被「要不要问用户」卡住，用户回来能一眼看到哪些是自己拍板的、哪些是 Agent 裁的。语义分几级、每级放哪见 `../developer_guide.md`「语义分级」。

本文只定规矩，不定用什么工具。穷尽解法时借助哪些工具，由开工指令决定，不写在这里。解法表怎么列、怎么剪、怎么推进在 `solution_table.md`。

## 两个阶段，两套权限

| | 一级（目的、用户体验与工具流程、架构、开发规则、Auto Mapping 文档） | 二级（产品功能） | 三级（机制） |
|---|---|---|---|
| **做计划时** | 用户拍板 | 用户拍板 | Agent 可改，改了告诉用户 |
| **执行时** | 不可改 | 穷尽解法表仍过不去：最小修改，标〔裁〕，告诉用户，不停 | 同二级 |

「告诉用户」的意思是把改了什么写给用户看（汇报、任务记录，有什么用什么），不等回复，不中断任务。

## 做计划

1. Agent 起草。要新增或修改的一级、二级内容以「修改前 / 修改后」列出来，连同 `../plan/` 里的施工计划一起交用户拍板。拍板前不开工。
2. 三级在计划阶段可以直接改：写进 `../mechanism/<链路>.md`，在计划里列出改了什么，告诉用户。Auto Mapping 的机制在 `../auto_mapping/`，属一级，同样等拍板。
3. 拍板后的一级、二级就是这次工作的验收标准，执行阶段逐条对照。

## 执行

- **一级不可改。** 达不到某条一级时，用解法表裁二级、三级：候选是二级、三级的裁法，方向是松哪一条承诺；一级不进表。裁过一次做不到，不算穷尽。表穷尽仍达不到，才把那一项标为「未达成」写进汇报，继续做其他项，不停。
- **二级、三级先穷尽解法表。** 卡住时按 `solution_table.md`：先从浅层（三级）找思路，再往深层（二级的裁法）逐渐递归；每条候选试之前先评有没有改善机制，说不出的剪掉，不为了证明做不到去撞墙；按分数扫，先试最有希望、最便宜的；一轮扫空后回顾一次还有没有没想到的路，有就再来一轮，评估确实没有了才放弃。不以失败次数或耗时为停下的条件。暂时性故障（断网、超时、构建被占、对端无应答）一律重试加退避，不算失败，不占表格里的一行。
- **穷尽后最小修改。** 只改卡住的那一处；在那一条后面标〔裁〕，写明试过什么（指向解法表的行号）、为什么不行、改成什么；当场告诉用户；然后继续往下做。
- **不停下来问用户。** 需要用户决定的事记进汇报的「待用户项」，其余工作照做。新增费用、需要人在机器旁的操作也不由 Agent 发起，记为待用户项，绕过去继续。
- 语义和代码冲突时按语义改代码，并在汇报里写明。

## 验证与汇报

- 每个阶段结束和整项工作结束时汇报：做了什么、验证证据（命令、通过数、看过的图，直接出现在对话里）、〔裁〕清单（每条附修改前后）、未达成项、待用户项、下一步。
- 用户回来审〔裁〕：可以推翻。推翻的部分返工，据它写的代码和计划一并改回。
- 验证没通过时改动保留在分支上，不回滚；汇报里写明哪项没过、为什么。

## 〔裁〕的写法

在被改的那一条末尾：

```
……原来的承诺或机制。〔裁 2026-09-28〕解法表 A、B、C 都因为 X 不行；改为 Y。
```

同时在本目录的任务记录里加一行，指向那个文件和那一条，解法表附在任务记录里。

## 任务记录

每项长时间工作在本目录一份 `<日期>-<任务>.md`，中断后从这份记录接着做：

```
# <任务>

拍板：<日期>，一级 / 二级改动指向哪些文件、哪几条
## 阶段与进度
- [ ] 阶段 1 …（完成的标志）
## 解法表（格式见 solution_table.md 第 5 节）
卡点：…　尺子：…
| # | 轮 | 级 | 父 | 候选 | 改善机制 | g | h | f | 验证 | 状态 | 结果 / 学到 |
## 〔裁〕清单
- <文件>:<条目> — 解法表第几行 … 不行 … 改为 …
## 未达成
## 待用户项
## 下一步
```
