# Tauri 迁移计划

2026-10-30。状态：方向已定；用户确认的一级、二级修改已落到本分支，还有五条待定（见「文档修改进度」）；代码未改。

来源：用户要在浏览器里快速调试、亲手试手感，两边界面一致，随后决定「现在定 Tauri」，并在审阅页逐条拍板。

## 目标

- 网页界面能完全替换 Qt 界面。
- 改界面和 Python 不用编译。改 C++ 只重编后端。
- 手感以 WebView2 为准，桌面和浏览器走同一条输入和绘制路径。
- Auto Mapping 的算法、`pyfile/` 的功能层、工程文件格式都不变。
- 仍是 Windows 桌面软件，仍是解压即用、离线可运行的压缩包。

## 最终目标与硬约束

最终目标：网页版能完全替换 Qt 版，`pyfile/` 不用改。

**验收：** 合并时 `git diff main -- pyfile/ pythonbind/animemodel.py opentoonz_tools/` 为空，`tests/t_*.py` 全过。为了合并而不得不改 Python 的地方，算迁移的缺陷，要改后端，不改 Python。

这条能成立，是因为 Python 看到的 C++ 接口可以保持不变：

| Python 用到的接口 | 规模 | 迁移后 |
|---|---|---|
| 模型：`SceneModel`、`VectorImage` 等 | 绑定 115 个，Python 用到约 86 个 | 内部改用纯 C++ 类型，名字和行为不变 |
| 几何：`vectorlogic`、`model_pybind` | 绑定 32 个 | 同上 |
| 界面门面 `ui` | 绑定 25 个，几乎都是单向通知 | 名字不变；现有回调槽换一组实现，转发给网页。查询类（主题、窗口列表）由后端缓存作答 |
| 钩子事件 `python_hooks.dispatch` | 40 处派发，`openglwidget.cpp` 里 141 行写消息字段 | 画板引擎组出**字段完全相同**的消息 |
| 菜单、设置窗、选项面板 | Python 返回 JSON，控件类型有 list、slider、check、button、color、subwindow、palette 等 | 网页按同一份 JSON 渲染 |

Python 仍然嵌在后端进程里，所以 `pydeps` 的 pip 自装、To 3D 的 `os.startfile` 都照常工作。Python 同步调用 `ui.*` 时不用等网页回复，界面通知异步发出，这也让网页不会被长计算卡死。

钩子消息是最容易悄悄走样的接口。第 5 步用录制比对来守住它：在 Qt 版上录下一批手势产生的消息序列，在新引擎上回放同样的输入，逐字段比较。

## 并行开发与合并

迁移在分支 `claude/tauri-migration` 上做，和代理图形（issue #7 及 #8–#12）并行，找合适的时机合并。Qt 文件可以改。

- **代理图形的 Python 部分直接带过来。** 分支不改 `pyfile/`，`pyfile/proxy_rect.py` 和 `auto_mapping.py` 的改动合进来没有冲突。
- **定期把 `main` 合进分支。** 这样 `mainwindow.*`、`openglwidget.*`、`algorithm/` 的冲突不会积压到最后。
- **盯住接口变化。** `main` 上新增的绑定、`ui` 函数、钩子消息字段或控件类型，每次同步时都要在后端和网页补上。#10（代理矩形的输入工具）如果新增 Qt 工具，就属于这一类。
- **分支上 Qt 版一直能编译。** 它是录制比对的基准，合并切换时才移除。

## 架构

```text
网页界面 + 画板渲染端（WebGL）
  是否基于 VibeFrontend，第 2 步评估后定
  ├─ tauri dev / 正式包：跑在 WebView2 里，浮动面板是独立窗口
  └─ 浏览器调试：跑在 Chromium 里
        │ 本地连接：输入、事件 ↓   状态、绘制列表 ↑
        ▼
旁路后端进程
  业务层 + 画板引擎 + 纯 C++ 计算层 + 嵌入式 Python（pyfile/）
```

开发时改动的代价：

| 改什么 | 要做什么 | 大约多久 |
|---|---|---|
| 界面、布局、交互逻辑 | 页面自动刷新 | 不用编译 |
| Python | 后端热重载 | 不到 1 秒（待实现） |
| C++ 后端 | 只重编后端，页面不关 | 5–12 秒（现有桌面版实测） |

## 实测依据

脚本在 `bench/`。绘制场景是合成的：1920×1080，每条笔画 40 段三次贝塞尔，显卡 RTX 3080。

| 项目 | 结果 | 脚本 |
|---|---|---|
| Python 层在 Pyodide 里的慢速倍数（已不走这条路，留作对照） | 中位 1.7 倍，范围 1.29–2.02 | `bench/run_one.py`、`bench/drive.py` |
| 浏览器 → Node → 原生 Python → 返回 | 1 个点 0.1–0.2 ms；映射 100 点 1.2 ms；映射 1000 点 10 ms | `bench/rtt/` |
| 落笔帧：已有笔画在缓存里，只重画当前一笔 | 3000、10000 条笔画都低于 1.3 ms 的测量下限 | `bench/layered.html` |
| 全量重画（3000 条笔画）：Qt CPU 栅格 | 约 1100 ms | `bench/main.cpp` |
| 全量重画（3000 条笔画）：Qt OpenGL 8x MSAA | 17–25 ms | `bench/main.cpp` |
| 全量重画（3000 条笔画）：Canvas 2D | 133–152 ms | `bench/canvas.html` |
| 全量重画（3000 条笔画）：WebGL，几何只上传一次 | 6–7 ms（接头简化，4x MSAA） | `bench/webgl.html` |
| C++ 全量编译加链接 | 25.8 秒，单文件重建 5–12 秒 | 临时构建目录，`--target AnimeAn --parallel 10` |
| 20 个 Python 模块连续重载两次 | 35 个钩子、5 个菜单不变，无残留旧函数 | 无界面测试，未在真程序里试过 |
| 计算层对 Qt 的依赖 | 7758 行里 1113 行用到 Qt 类型 | 代码统计，见第 1 步 |

`bench/devbench/` 是最小的浏览器试验台：Node 监视 `pyfile/`，存盘约 0.4 秒生效。它用 Pyodide，只验证过热重载的体验，不是正式方案。

## 施工顺序

总工作量约 14–21 周，第一个能用真后端画线、跑映射的版本约 9–14 周。这些是估算，没有依据可引。比上一版多的时间来自计算层去 Qt 和独立窗口。第 6 步的时间要等第 2 步的评估结果再重估。

0. **真笔门槛。** 用真数位板在 WebView2 里测采样率、压感和系统手势，和 Qt 版画同样的线对比。
   预计半天。通过标准：样本数不低于 Qt 版的 80%（这个门槛是提议，可改），没有系统手势抢笔。不通过就回到 Qt 路线。
1. **计算层去 Qt。** 把 `algorithm/`、`projectio.*`、`clipreader.*` 改成不依赖 Qt 的纯 C++。Qt 主程序在边界上转换类型，继续能跑。
   顺序：先换 `QPointF`、`QVector`、`QString`、`QJson` 这些基础类型（量大但简单）；再换 `QPainterPath` 的布尔运算和描边（`vectorlogic.cpp` 的填充区域，第 2605、2666、2679、2746 行）；最后处理撤销快照依赖的隐式共享（`scenehistory.h`）。
   预计 3–5 周。完成标志：`animean_core` 不链接 Qt；`ctest` 和 `tests/t_*.py` 全过；Qt 版行为不变，填充结果和替换前逐例比较。
2. **评估 VibeFrontend 的结果。** 那边完成后，判断在它的基础上打补丁加翻译，还是重写界面。
   预计 2–3 天。产出：结论和第 6 步的新估算。
3. **无界面后端。** 业务层（参考 VibeFrontend PR #4，换成纯 C++ 类型）、本地连接协议、Python 热重载。
   预计 1–2 周。完成标志：不开窗口也能新建工程、加图层、撤销；改 `.py` 不到 1 秒生效。
4. **Tauri 外壳接后端。** 启动和回收旁路进程，建立主窗口和独立的浮动面板窗口。
   预计 1–1.5 周。完成标志：网页里的图层面板操作的是真模型；浮动面板能拖到第二块屏幕。
5. **画板引擎和 WebGL 渲染端。** 从 `PaintOpenGLWidget` 抽出采样、手势和覆盖层，变成不依赖 Qt 的引擎，输出绘制列表。这是最大的一步。
   预计 3–5 周。完成标志：两块板能画线、擦除、拖轴线、跑 Auto Mapping；录制的钩子消息回放后逐字段一致；同一工程和 Qt 版对比，除抗锯齿外一致。
6. **补齐面板。** 按现有长相做菜单、工具、选项、时间轴、调色板、对话框、导入。
   预计 4–6 周。完成标志：按 `../../tools_user_workflow/README.md` 列出的工具页逐页手测通过。
7. **打包和合并。** Tauri 与后端打成压缩包，在离线的新机器上验证，然后找时机合并进 `main`。
   预计 1 周。完成标志：`pyfile/` 差异为空，`tests/t_*.py` 全过。合并和删除 Qt 界面代码都由用户确认。

**手势和把手的核实结果：**

- 手势：画板上一次按下、移动、松开的鼠标或笔操作，不是触屏的多指手势。C++ 把它换算成文档坐标，做稳定器、吸附等处理，再按当前工具路由。
- 把手：画板上可以拖动的小控制点（`EditHandle`：id、位置、形状、颜色）。Python 决定有哪些、代表什么，底层只负责显示、命中和上报。
- 把手事件（`handle`）比把手本身宽：`arm`、`pick`、`hover`、`view` 这些阶段不需要命中把手，它实际上是所有编辑类工具的事件入口。
- 迁移后原始笔输入由网页采集，所以「手势采集」要改成「手势处理」。

## 风险

- **真笔未测。** 第 0 步就是为了尽早发现这个问题。
- **计算层去 Qt 改变结果。** 换掉 `QPainterPath` 的布尔运算后，填充边界可能和现在有细微差别。这部分要逐例比较，Auto Mapping 的结果不能变。
- **长期分支的冲突。** `mainwindow.*`、`openglwidget.*`、`algorithm/` 两边都会改，不定期同步，最后的合并会很难。
- **接口悄悄走样。** 钩子消息少一个字段，Python 不一定报错，只是行为变了。要靠录制比对发现。
- **手感要重新调。** 输入路径变了，稳定器和拟合参数可能要调。这些参数改动是三级；Auto Mapping 的常量仍是一级。
- **画板引擎难拆。** `openglwidget.cpp` 有 4424 行，界面和逻辑混在一起，估算的不确定性最大。
- **独立窗口。** 纹理板能在中央页、子控件框、停车位之间搬迁，变成跨窗口搬迁后，canvas 和 WebGL 上下文要重建，这部分还没有验证。
- **低端显卡没有数据。** 全部绘制数字来自 RTX 3080。
- **绘制结果不会逐像素相同。** WebGL 和 QPainter 的抗锯齿不同，笔画形状以后端的路径为准。
- **WebView2 自动更新。** 引擎版本由系统更新，发布时要确认是否随包固定版本。

## 不做

- 不改 `pyfile/`，也不把里面的算法搬到 C++ 或 Rust。
- 不用 Rust 重写 C++ 核心。
- 不做 wasm 版后端。
- 不做网页版发布：浏览器只用于开发调试。
