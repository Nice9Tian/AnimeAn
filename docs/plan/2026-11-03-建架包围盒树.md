# 建架提速：包围盒树求交与按架缓存的可折判定

PR #18 的方案 B。用户 2026-11-03 定：只从 #18 拆出建架部分，解算器（`chord_intersect` 的反解分流）先不拿，#18 保留不关；结果必须和改动前逐位相同；分格常数、耗时这类数字不进一级文档，留在代码和本计划里。评估见 PR #18 的评估报告（2026-11-02）。

## 改了什么

- **导引线求交。** `_polylines_cross`、`_polyline_intersection`、`_curve_crossing` 不再逐段双重循环，改走新模块 `pyfile/polyline_boxes.py` 的两棵包围盒树。`box_pairs` 按双重循环的 (i, j) 序给出可能相交的段对，包围盒按求交的 eps 放宽，第一个相交的就是双重循环的那一个；不相交时 `closest_vertices` 用同样的平手规则给出最近的顶点对。这三个函数照搬 #18 的 `chord_intersect.py`，为了逐位相同另加了两处：
  - **近平行的段对不靠包围盒剪掉。** `_segment_intersection` 的平行判据是绝对值 `1e-12`，长一点的段几乎碰不到它。两段近平行时它算出的参数是舍入噪声，包围盒相离也可能落进容差，双重循环就报出并不存在的交点，例如两条共线、相距 300 px 的 300 px 段。#18 原样的包围盒树会剪掉这对，结果就和原来不同。现在每个树节点记下它的段方向所占的弧（倍角，正反向算同一条线），只有包围盒相离、并且方向离平行都超过 `_PARALLEL_SIN = 1e-7` 时才剪。离平行更远时，参数的舍入误差一阶上不超过段长乘 18·2⁻⁵³/sin(夹角)，sin 大于约 2e-9 就远小于包围盒放宽的 1e-6，所以剪掉的段对不可能被双重循环接受；1e-7 留了 50 倍余量。
  - **空折线照旧报错。** 少于两个点时 `closest_vertices` 就是原来的双重循环，空列表照旧抛 `TypeError`。调用方都先查过两点以上，正常走不到。
- **可折判定。** `can_fold` 从 `build_mapper` 的闭包挪到 `_Frame.can_fold`，结果缓存在架上，`_reused_frame` 复用的架不再重算。「全部方向对取最小值」改成每个 v 方向在排序后的 h 方向里取离目标角最近的两个。排序查找只在角度被舍入成相同的方向之间会选错，差在 1e-15 以内，所以只有最小值离 `_SEVER_GATE_SIN` 不到 1e-12 时判定才可能和逐对比较不同；那时改为逐对比较全部方向对，判定与原来完全相同。`_Frame.hand()` 和 `build_mapper` 里的 `child_hand` 是同一个式子。
- **没拿。** `ChordIntersect`、`solve_full` 的分流、`_descend`，以及 #18 改的一级文字（那些写的是解算器）。

## 结果相同的证据

- `tests/t_frame_build.py`，种子与 #18 `t_frame_solver` 第 4–7 节相同，所以那几节是同样的架：
  - 可折判定：300 个随机架；卡在闸门上的 162 个架，其中一半的 h 是切成 1,200 段的直线、方向近乎重复；一个分量只差 1 ulp 的平手架。全部与原来的闭包（逐字照搬进测试）相同。
  - 求交：1,400 组折线对；7 组字面的近平行反例和 4,000 组近共线的段对；3,000 组跨过 200 万 px 长段端点的短段（长段一侧的 eps 有 2 px）；120 对曲线导引线；空折线和单点折线。全部与双重循环逐值相同。
  - 变异检查：段对改成先 j 后 i、平手规则改成取最后一对、去掉方向弧、去掉闸门旁的逐对复核，这个测试都会失败。
- 近平行模糊测试：同一批 300 万组近共线段对（夹角的 sin 从 1e-13 到 1e-4，坐标到 1e8），#18 原样的包围盒树有 22 组和双重循环不同，现在 0 组；另两个种子共 420 万组，也是 0 组。
- 同一批架改动前后逐位比较（#18 评估用的 11 种架加示例工程 `tests/fixtures/additional_line_axis_notch.anproj`）：每个探针的判定、弧长坐标和映射点，每条笔画的岛数、裁掉的长度和映射后的每个点，全部相等，0 处不同。
- 示例工程整体重算 `_run`、拖纹理 H 轴 40 步、拖附加线之后，主画板上的映射笔画逐点相差 0 px。
- `py -m unittest discover -s tests`：通过（32 个 `t_*.py`，含新的 `t_frame_build.py`）。
- Argon-High 交叉审核两轮。第一轮审的是 #18 原样的版本，查出的两处真问题就是上面两处（共线远离段的假交点、闸门上 1 ulp 的平手），反例已收进测试；空折线报错类型不同、长段一侧的 eps 没测到、双螺旋只计时一次、本计划写法不准，也都已改。它认为一级复杂度表写进了实现细节；按 `developer_guide.md`「Auto Mapping 的机制写 `auto_mapping/`（一级）」，这几行留在一级，只改得更短。第二轮审方向弧和闸门复核，没有找到问题：它另做了 40 万组对抗构造，其中 32 万组是被剪掉的段对，双重循环接受的 0 组；两种查法的闸门最小值实测最多差 3.3e-16，1e-12 的复核窗口有三个数量级的余量。

## 耗时

本机 i7-14700KF，只算 Python，一个进程跑一棵树，每项取多遍里最快的。

- 3000×3000 的架：建架（求交）加一次反解 1,155 ms → 7.9 ms；可折判定 265 ms → 2.0 ms（改动前的判定是 `build_mapper` 里的闭包，计时时照原样搬出来算同一个架）。
- 示例工程的两个架（曲线导引线，131×110 和 77×66 个点）：纹理板 2.81 → 1.24 ms，主画板 1.29 → 0.98 ms。#18 原样的包围盒树是 1.12、0.91 ms，方向弧多花约 0.1 ms。拖纹理轴时每帧都要重建纹理板的架，每帧省下约 1.6 ms。
- #18 评估用的架（两块板各建一次架）：jitter301 11.7 → 0.85 ms，bow30、bow60、bow100、S 曲线约 1 ms → 0.3–0.4 ms；直线和很短的架本来就在 0.1 ms 左右，几乎不变。
- 最坏情形是两条缠绕的双螺旋：包围盒处处重叠，方向每圈都转回来，方向弧挡住了很多包围盒相离的节点对，约 210 ms（#18 原样约 25 ms，双重循环要数秒）。`t_frame_build.py` 第 5 节给普通架和不相交的架各留 0.5 s、双螺旋留 1 s；双重循环在普通架上就要一秒以上，退回去会失败。（2026-11-14 起第 5 节不再卡秒数：改数建架、求交时实际做了几次精确线段求交，并要求走 `polyline_boxes.box_pairs`；退回双重循环照样失败。）

## 须知

- 双重循环在共线、相距很远的段上会报出假交点（平行判据是绝对值），这里为了逐位相同照样保留。要修是另一件事：一些退化画法下的提示会变。
- 方向弧的界是一阶估计，常数取得宽，再留 50 倍余量；模糊测试在 sin 低到 1e-13 的段对上没有找到反例。
- 以后要接 #18 的解算器，先让它改用 `polyline_boxes`，不要再带一份包围盒树。
