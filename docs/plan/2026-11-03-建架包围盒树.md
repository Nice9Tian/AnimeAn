# 建架提速：包围盒树求交与按架缓存的可折判定

PR #18 的方案 B。用户 2026-11-03 定：只从 #18 拆出建架部分，解算器（`chord_intersect` 的反解分流）先不拿，#18 保留不关；结果必须和改动前逐位相同；分格常数、耗时这类数字不进一级文档，留在代码和本计划里。评估见 PR #18 的评估报告（2026-11-02）。

## 改了什么

- **导引线求交。** `_polylines_cross`、`_polyline_intersection`、`_curve_crossing` 不再逐段双重循环，改走新模块 `pyfile/polyline_boxes.py` 的两棵包围盒树。`box_pairs` 按双重循环的 (i, j) 序给出可能相交的段对，包围盒按求交的 eps 放宽，所以第一个相交的就是双重循环的那一个；不相交时 `closest_vertices` 用同样的平手规则给出最近的顶点对。代码照搬 #18 的 `chord_intersect.py`，只拿了这三个函数。
- **可折判定。** `can_fold` 从 `build_mapper` 的闭包挪到 `_Frame.can_fold`，结果缓存在架上：`_reused_frame` 复用的架不再重算。「全部方向对取最小值」改成每个 v 方向在排序后的 h 方向里取离目标角最近的两个，最小值相同。`_Frame.hand()` 和 `build_mapper` 里 `child_hand` 是同一个式子。
- **没拿。** `ChordIntersect`、`solve_full` 的分流、`_descend`，以及 #18 改的一级文字（那些写的是解算器）。

## 结果相同的证据

- `tests/t_frame_build.py`：#18 `t_frame_solver` 第 4–7 节，种子相同，所以是同样的架。1,400 组折线对上求交和双重循环逐值相同（566 组相交，834 组走最近顶点）；300 个随机架上可折判定和全部方向对的最小值一致（177 个可折，123 个不可折）。另加 120 对曲线导引线，`_curve_crossing` 和改动前的函数逐值相同。把段对顺序改成先 j 后 i，或把平手规则改成取最后一对，这个测试都会失败（变异检查）。
- 同一批架改动前后逐位比较（#18 评估用的 11 种架加示例工程 `tests/fixtures/additional_line_axis_notch.anproj`）：每个探针的判定、弧长坐标和映射点，每条笔画的岛数、裁掉的长度和映射后的每个点，全部相等，0 处不同。
- 示例工程整体重算 `_run`、拖纹理 H 轴 40 步、拖附加线之后，主画板上的映射笔画逐点相差 0 px。
- `py -m unittest discover -s tests`：通过（32 个 `t_*.py`，含新的 `t_frame_build.py`）。

## 耗时

本机 i7-14700KF，只算 Python，一个进程跑一棵树，每项取三遍里最快的。

- 3000×3000 的架：建架（求交）加一次反解 1,155 ms → 5.0 ms；可折判定 266 ms → 1.9 ms（改动前的判定是 `build_mapper` 里的闭包，计时时照原样搬出来算同一个架）。`t_frame_build.py` 第 5 节在同样的架上给求交、判定和首次反解合计留 0.5 s，两条导引线不相交、缠绕双螺旋两种情形也一样；双重循环在这里要一秒以上，退回去就会失败。
- 示例工程拖动时的提速来自这两处，评估报告实测纹理轴每帧的求交约 1.7 ms、可折判定约 0.5 ms，每帧最多快约 5%。

## 须知

- 包围盒树和双重循环等价，靠两点：段对按 (i, j) 序给出，包围盒按 eps 放宽了两倍。两段夹角在 1e-12 弧度量级时，浮点误差理论上能让双重循环接受一对包围盒相离的段；手画和程序生成的导引线都画不出这种段，测试里也没有出现。
- 可折判定只在最小值离 `_SEVER_GATE_SIN` 不到几个 ulp 时，理论上可能和逐对比较不同。
- 以后要接 #18 的解算器，先让它改用 `polyline_boxes`，不要再带一份包围盒树。
